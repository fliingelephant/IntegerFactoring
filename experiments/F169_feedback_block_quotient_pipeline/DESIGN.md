# F169-D01 frozen design

## 1. Stage order

Process one modulus at a time. Do not process moduli in parallel.

At the base stage:

1. freeze the ordered seed list;
2. run unit and direct-sign gcd screens;
3. append each exact value to the relation ledger;
4. append both endpoints to the presentation ledger, even when the exact
   value is a duplicate;
5. rebuild and decode the relation ledger;
6. rebuild the endpoint gcd-free basis;
7. saturate the frozen endpoint-block pool under P154.

At feedback level `h` in `{1,2}`:

1. freeze the relation basis before the level starts;
2. freeze all support-one and support-two candidates and their order;
3. compute every candidate from that frozen basis only;
4. stop immediately if a public direct gcd is proper;
5. otherwise append its exact relation and both endpoint occurrences;
6. only after the level ends, rebuild both ledgers;
7. stop if the union decoder gives a non-global root;
8. freeze the newly exposed endpoint blocks;
9. saturate that frozen pool under P154.

New exact records cannot alter the source basis inside the current level.
P154 state updates cannot alter the current or past source menus.

## 2. The two ledgers

### 2.1 Relation ledger

Each record stores:

- exact positive value `A`;
- supplied modular root;
- first source stage and all later occurrences;
- complete recursive source provenance.

Deduplicate by exact `A` only after checking the ratio of supplied roots. A
non-global ratio is an immediate normalized-root certificate. The complete
factor-free parity decoder and its first-occurrence decorated basis use this
ledger only.

### 2.2 Presentation ledger

Each endpoint occurrence has a unique occurrence index. It stores:

- integer endpoint value;
- role `left` or `canonical_inverse`;
- source stage;
- source record or section subset;
- recursive provenance to base relation columns.

No endpoint occurrence is deleted. Rebuild the deterministic gcd-free basis
from all endpoint occurrences after each frozen stage. The implementation
must preserve an exponent signature for every occurrence and verify exactly

```text
endpoint[i] = product(block[j]^signature[j][i]).
```

It must also verify that all terminal blocks are larger than one, pairwise
coprime, and units modulo `N`. Perfect-power extraction is allowed because
the occurrence exponents are retained. Integer factorization is forbidden.

The implementation must pin or independently reproduce the
`deterministic_gcd_basis` semantics from the frozen F157 source. A different
basis convention requires a new registration.

## 3. Block identity and provenance

Sort a stage's terminal blocks by integer value. Keep every first-seen block
as a historical public generator.

- `creation_stage(d)` is the first stage whose terminal basis contains `d`.
- `d` is base-visible when `creation_stage(d)=0`.
- `d` is feedback-only when `creation_stage(d)` is one or two.

When a later basis splits a historical block, store the exact decomposition
of the historical integer into current terminal blocks. A new proper
descendant is feedback-only even when its occurrence signature includes a
base endpoint. A cofactor supported only on new endpoints is also
feedback-only.

This label concerns public integer representation access. It does not claim
that the residue lies outside the subgroup generated by the base blocks.

## 4. Certified initial state and caps

For odd `N`, `g=N-1` has exact order two in every hidden prime-power
component. Verify

```text
g^2 = 1 mod N
gcd(g-1,N) = 1
gcd(2,N) = 1.
```

Set `M=2`. Retain the factorization of every later `M`.

For `n=N.bit_length()`, set

```text
B = n*n
C = n*n.
```

These are fixed public polynomial, hence quasipolynomial, caps. The finite
test makes no inference about larger caps.

## 5. Factor-first fixed-point updater

At one frozen endpoint stage, order generators as follows:

1. blocks created at the current stage, in increasing integer order;
2. older historical blocks, by decreasing creation stage and then increasing
   integer value.

Repeat the following pass until there is no strict state growth.

1. Verify the current common-order certificate and `gcd(M,N)=1`.
2. For each frozen block in order, run the complete P154 absolute screen.
3. On the absolute-hard branch, run every relative exponent `1<=e<=B` in
   order.
4. A proper gcd stops the modulus.
5. A common absolute or relative return invokes the P150 common-order
   construction. If its order is larger than `M`, store the new state,
   discard all fingerprints, and restart the pass.
6. If all one-block scans finish without growth, run the P154 BFS on the
   complete frozen historical pool in the same generator order.
7. A proper fingerprint-difference gcd stops the modulus.
8. Closed order `kappa>1` invokes P150, stores order `M*kappa`, discards all
   fingerprints, and restarts the pass.
9. Closed order one is inert. Storing `C+1` distinct fingerprints is the
   capacity outcome. Either outcome ends this stage.

The relative scan can update powers iteratively. It must still report the
first exponent whose gcd is not one.

## 6. Complete capped BFS

Start from fingerprint one. Use a FIFO queue. For each dequeued word, multiply
by every frozen generator in order.

Before insertion or deletion, compare the candidate with every stored
fingerprint by `gcd(y-z,N)`. This includes comparison with the globally equal
stored value. A proper gcd stops. A globally new value is inserted with one
predecessor index and one generator index. A globally duplicate value is not
inserted after all comparisons finish.

Stop only when:

- a proper gcd appears;
- the queue closes; or
- `C+1` globally distinct fingerprints have been stored.

On closure, verify every generator edge stays in the table. Factor `kappa`
by trial division. Recover a table generator and its endpoint-block word. On
capacity, retain all `C+1` values and their predecessor data as the replay
certificate.

## 7. Feedback attribution

Every factor certificate records the two compared public words. Every state
growth certificate records the public word used by P150.

Define its **difference word** as the exponent difference of the two
fingerprint words for a factor, or as the P150 generator word for growth.
The event is feedback-dependent only when this word contains a block with
creation stage one or two with nonzero exponent.

Also record two weaker labels:

- `later_base_only`: the event occurs after feedback, but its difference word
  uses only base-visible blocks;
- `feedback_triggered_under_cap`: the registered base pass returned no
  factor or growth, and the later word uses a feedback-only block.

Do not call the second label abstract subgroup enlargement when the base BFS
ended at capacity. The base subgroup was not completely enumerated there.

## 8. Public metrics

Record these values for every modulus and stage.

### Source and relation decoder

- attempted candidates;
- direct-sign outcome counts;
- strict exact values and duplicates;
- relation rows, columns, rank, nullity, and normalized-root status;
- hashes of candidates, exact values, parity blocks, and selected basis
  columns.

### Presentation ledger

- endpoint occurrences and distinct endpoint values;
- terminal blocks and occurrence incidences;
- preserved, split, and newly created blocks;
- new descendant blocks and new probe-only cofactors;
- counts split by base-visible and feedback-only status;
- hashes of endpoints, signatures, blocks, and provenance.

### P154 updater

- every certified state `(g,M)` and its public word;
- absolute outcomes `proper`, `global`, and `hard`;
- relative outcomes `proper`, `common e`, and `above B`;
- strict state updates and reset count;
- BFS generator count, candidate edges, pair comparisons, stored values, and
  outcome `factor`, `closed`, or `capacity`;
- closed `kappa`, or the certified lower bound `M*(C+1)`;
- first factor or growth certificate and its attribution label;
- final state and final obstruction on a null input.

Aggregate the number of inputs stopped at the base, eligible for level one,
eligible for level two, and successful only through a feedback-dependent
P154 event.

## 9. Public replay and private diagnostics

Every positive certificate has an `N`-only replay.

- A factor replay reconstructs its endpoint and state provenance and repeats
  the ordinary gcd.
- A state replay verifies `h^M=1 mod N` and the prime-divisor exact-order gcd
  screens for the claimed new `M`.
- A closed-table replay checks every edge and generator claim.
- A capacity replay rebuilds the stored table and all pair comparisons.

Only after the public result is frozen may the runner use the disclosed
`p,q` to label a proper factor or to report local absolute and quotient
orders. Private local orders cannot select blocks, candidates, generator
order, caps, stopping points, or certificates.

## 10. Resource boundary

The prior frozen F165 transcript reports at most 948 endpoint positions and
at most 325 candidates in one level on this corpus. On every stage that F169
actually reaches, it must reproduce the corresponding F165 relation-source
hashes before its new endpoint and updater metrics are accepted. An input
that F169 stops earlier on a proper factor is excluded from later hash
comparisons; it is not silently treated as a null stage.

For this 27-bit corpus, `B=C=729`. Store BFS provenance as predecessor pairs,
not copied word vectors. Process one modulus at a time. Do not keep product
trees from completed stages or moduli.

Estimated peak memory is below 2 GB. The named hard timeout is 1200 seconds.
Before an authoritative run, inspect macOS memory pressure and competing
processes. Do not start unless at least 6 GB is available and memory pressure
is normal. Record the preflight result in the run log. No computation is
authorized by this design document.

## 11. Inference boundary

A positive result is a fixed public capability certificate. A null result is
a finite obstruction for this exact source, depth, corpus, caps, and order.
Neither result proves a density, a minimum feedback depth, an independent
capacity law, or an all-input quasipolynomial factoring theorem.
